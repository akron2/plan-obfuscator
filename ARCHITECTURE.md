# Архитектура: локальный Plan Obfuscator на Python

Статус: зафиксировано для реализации  
Дата: 2026-10-13

## Цель и критерии успеха

Plan Obfuscator — основное локальное Windows-приложение для обратимой
обфускации Oracle SQL, `DBMS_XPLAN`, SQL Monitor `TEXT`, outline и predicates
перед ручной передачей материалов в ChatGPT, Claude или другую модель.

Готовый продукт должен:

1. Запускаться через `run.bat`, самостоятельно создавать `.venv` и ставить
   зависимости только тогда, когда их действительно не хватает.
2. Поддерживать `--proxy`, `--port`, `--data-dir` и `--no-browser`.
3. Работать только локально на `127.0.0.1` и не обращаться к API моделей.
4. Хранить в SQLite кейсы, материалы, ревизии, mappings, сформированные prompts,
   сырые ответы ИИ и восстановленные ответы.
5. Поддерживать несколько планов и SQL Monitor запусков одного логического SQL
   внутри кейса.
6. Автоматически отличать Oracle-материал, вопрос и ответ ИИ; при реальной
   неоднозначности давать пользователю три понятных варианта.
7. Согласованно заменять одинаковые сущности во всех материалах кейса.
8. Сохранять диагностические метрики и форматирование исходных материалов.
9. Точно восстанавливать собственный обфусцированный текст и безопасно
   восстанавливать известные маркеры в ответе модели.
10. Проходить единый Oracle corpus, включая реальные Docker-отчёты, смешанный
    ввод, усечённые отчёты и автоматически сгенерированные варианты.

## Ограничения и допущения

- Основная ОС — Windows.
- Целевая версия Oracle — 19c; corpus Oracle XE 21c используется как
  дополнительная проверка совместимости форматов.
- SQL Monitor поддерживается в формате `TEXT`.
- Один кейс соответствует одному логическому SQL, но содержит сколько угодно
  связанных планов, child cursors и выполнений.
- Обмен с моделью выполняется вручную: `Копировать prompt` и вставка ответа
  обратно в приложение.
- Старая SQLite-база не обязана мигрировать в новую схему. До публичного релиза
  используется чистая начальная схема.
- SQLite не шифруется: приложение рассчитано на доверенный локальный контур.
- История хранится без автоматического срока удаления.
- Расширение Chrome остаётся экспериментом и не определяет основную архитектуру
  или критерии готовности Python-продукта.

### Разбор Oracle

Python является единственным источником истины. Сохраняются SQLGlot с Oracle
dialect, собственный lexer и section-aware parsers. TypeScript во время работы
приложения не запускается.

Из экспериментального расширения в Python переносятся подтверждённые corpus
правила:

- `EXPLAINED SQL STATEMENT` и `SQL STATEMENT`;
- Peeked Binds как с именем, так и только с позицией;
- табличные SQL Monitor binds `Name | Position | Type | Value`;
- DDL, DML, PL/SQL, database links, JSON, hierarchy, PIVOT и parallel layouts;
- несколько XPLAN/SQL Monitor отчётов в одном вводе;
- fenced SQL вместе с отчётом и обычным поясняющим текстом;
- корректное разделение identity values и performance metrics;
- fail-closed обработка усечённых или неизвестных Oracle-подобных секций.

Парсер возвращает точные диапазоны исходного текста. Результат строится заменой
диапазонов, а не повторной генерацией SQL.

### Пользовательский поток

1. Пользователь создаёт кейс.
2. В единое поле вставляет SQL, план, мониторинг, outline, predicates или файл.
3. Если в одной вставке несколько материалов, приложение разделяет и добавляет
   их одной операцией.
4. Обычный текст после добавления контекста считается вопросом.
5. Приложение создаёт неизменяемый запуск, формирует prompt и показывает кнопку
   `Копировать prompt`.
6. Пользователь вручную отправляет prompt выбранной модели.
7. Вставленный ответ с маркерами автоматически распознаётся, сохраняется в сыром
   виде и отображается после обратного преобразования в оформленном виде
   (см. «Ответы ИИ: вставка и отображение»).
8. По умолчанию виден последний цикл; вся история открывается переключателем.

Если материал содержит другой независимый SQL, он не присоединяется молча:
интерфейс предлагает создать новый кейс.

### Mapping и восстановление

Mapping изолирован одним кейсом. Маркер имеет формат
`OBF_<prefix>_<type>_<number>_<check>`. Номера не переиспользуются.

Используются два режима:

- exact restore собственного результата по сохранённым occurrences;
- восстановление ответа ИИ по целым валидным маркерам из mapping.

Повреждённые и неизвестные маркеры остаются в тексте и показываются как
предупреждение. Нечёткое восстановление запрещено.

### Ответы ИИ: вставка и отображение

Проблема: ответ ChatGPT или Claude, скопированный вручную, попадает в
`<textarea>` только как `text/plain`. Восстановленный ответ показывается в
`<pre>`. В результате таблицы, блоки кода, заголовки, списки и диаграммы
превращаются в сплошной текст, а соседние блоки склеиваются: карточка
«План №1 / 9 326» становится `План №19 326`.

Что ChatGPT кладёт в буфер (проверено 2026-10-13 на реальном ответе; образцы
буфера используются как test fixtures):

| Элемент | Кнопка «Копировать ответ», `text/plain` | Выделение мышью, `text/plain` | `text/html` (оба способа) |
|---|---|---|---|
| Заголовки, списки | Markdown | плоские строки | `h1–h3`, `ul/li` |
| Таблица | Markdown-таблица | TSV или каждая ячейка отдельной строкой | `table` либо фрагменты `table/tbody` |
| Блок кода | язык отдельной строкой перед fence | без границ блока | `pre/code` |
| Mermaid | текст схемы | текст схемы | текст схемы в `pre/code` |
| Жирный текст | теряется | теряется | задан CSS-классами, не тегами |
| Диаграмма, карточки | превращаются в заголовки `## 9326` | подписи и числа подряд | блоки `data-d-component` с подписями, числами, цветом и шириной |

Вывод: надёжный источник структуры — `text/html`. Его разметка может быть от
нескольких KB на публичной share-странице до примерно 190 KB в основном чате и
содержать служебные атомарные CSS-классы и комментарии framework, поэтому нужен
собственный конвертер с обязательным fallback на текст.
HTML Claude не проверялся; ожидается обычная семантическая разметка.

Поток данных:

```text
paste в composer
  ├── textarea  ← text/plain (пользователь видит и может править)
  ├── JS-память lastPastedPlain ← исходный text/plain этой вставки
  └── hidden pasted_html ← text/html (только если это не SQL/план и ≤ 10 MiB;
                            очищается в JS при любой правке textarea)
        │
        ▼ POST (max_part_size = 100 MiB)
classify(text) ──► material/question: pasted_html отбрасывается
        │
        └─► response:
              pasted_html непустой (и совпадает с pasted_plain, если он передан в API)?
                 да  → clipboard_html_to_markdown(pasted_html)
                 нет → normalize_plain_answer(text)
              ▼
          Response.raw_text = Markdown с OBF-маркерами
```

Правила:

1. **Вставка в браузере не меняет текст и не раздувает форму.** JavaScript
   сохраняет `text/html` последней вставки в скрытое поле `pasted_html` только в
   том случае, если вставленный текст не является очевидным Oracle-материалом
   (SQL, `DBMS_XPLAN`, SQL Monitor, Outline, Predicates), режим не зафиксирован
   как `material`/`question`, а размер `text/html` не превышает `10 MiB`
   (`MAX_CLIPBOARD_HTML_CHARS`). Полная копия `text/plain` повторно по сети в
   скрытом поле формы не пересылается. Решение о конвертации принимает сервер
   после классификации. Oracle-материалы, в том числе HTML из Toad, DataGrip или
   SQL Developer, всегда обрабатываются как `text/plain`.
2. **Проверка соответствия без дублирования трафика.** В браузере `app.js`
   хранит вставленный `text/plain` в памяти (`lastPastedPlain`) и сравнивает его
   с текущим значением `textarea` после нормализации переводов строк. Если
   пользователь вставил фрагмент в середину существующего текста или изменил
   текст после вставки (в том числе после серверного запроса выбрать режим),
   `pasted_html` немедленно очищается на клиенте. На сервере опциональный
   параметр `pasted_plain` сохраняется для обратной совместимости JSON API и
   модульных тестов: если он передан явно, сервер дополнительно сверяет его с
   `text`.
3. **`clipboard_html_to_markdown`** — модуль на стандартном `html.parser`, без
   новых зависимостей:
   - семантические теги (`h1–h6`, `p`, `ul/ol/li`, `table`, `pre/code`,
     `strong/b`, `em/i`, `blockquote`, `a`) переводятся в GFM Markdown;
   - блочные элементы (`div`, `section`, `p` и `data-d-component` box/row/text)
     всегда разделяются переносом строки — это устраняет склейку;
   - язык блока кода берётся из `class="language-…"` или из подписи блока;
     `mermaid` сохраняется как fenced block `mermaid`;
   - распознанные диаграммы и карточки ChatGPT (повторяющиеся пары
     «подпись — число» внутри box/row) переводятся в таблицу
     «Показатель | Значение»; нераспознанные блоки становятся абзацами;
   - `button`, `svg`, `img`, скрытые элементы, комментарии, стили и атрибуты
     отбрасываются;
   - символы Markdown в обычном тексте экранируются, но OBF-маркеры
     не экранируются никогда (`OBF_A1_…` не превращается в `OBF\_A1\_…`).
4. **`normalize_plain_answer`** — fallback для текста без HTML:
   - одиночная строка с языком (`sql`, `mermaid`, …) перед fenced block
     переносится в info string;
   - группа строк с одинаковым числом табуляций превращается в
     Markdown-таблицу;
   - остальное не меняется.
5. **Хранение.** `raw_text` хранит Markdown с маркерами, `restored_text` —
   Markdown после восстановления (для «Копировать ответ»). Исходный HTML
   буфера не сохраняется. Схема SQLite не меняется.
6. **Отображение.** Сервер рендерит `raw_text`, а не `restored_text`:
   - Markdown → HTML через `markdown-it-py` (CommonMark + таблицы,
     сырой HTML запрещён, опасные ссылки отклоняются);
   - Markdown-изображения не создают `<img>` и не вызывают внешних запросов;
     показывается только безопасный текст подписи;
   - Markdown сначала разбирается в дерево токенов; затем маркеры заменяются
     оригиналами только в текстовых, inline-code и fenced-code токенах;
   - токены сериализуются в HTML, причём обычный текст экранирует renderer, а
     блоки кода безопасно экранирует и подсвечивает `Pygments`.

   Порядок «сначала разбор Markdown, потом восстановление» гарантирует, что литерал
   вроде `'a*b*c'` или идентификатор `V$SQL` показывается буквально, а не
   интерпретируется как Markdown.
7. **Mermaid.** Блоки `mermaid` рисуются в браузере локальной копией
   `mermaid.min.js` (`static/vendor/`, загружается только при наличии таких
   блоков, `securityLevel: "strict"`). Задаются явные `maxTextSize` и `maxEdges`;
   слишком большая или ошибочная схема остаётся исходным кодом. Внешние ресурсы
   не загружаются.
8. **Переключатель.** У ответа есть «Оформленный / Исходный текст». Исходный
   текст — текущий `<pre>` с `restored_text`.
9. Ответы, сохранённые до изменения, рендерятся тем же путём в режиме best effort.
   Совместимость старого визуального представления не требуется; ценная БД
   отсутствует. Отдельная миграция и `format_version` не нужны.

Не переносится и принимается как ограничение:

- цвета и оформление сайта чата: у нас собственный стиль;
- жирный текст из HTML ChatGPT: он задан классами, а не тегами;
- изображения: их URL требуют авторизации в чате и быстро истекают;
- точный вид диаграмм: они превращаются в таблицу значений.

### SQLite

Сохраняется нормализованная модель: case, artifact, revision, symbol, run,
run-artifact, replacement, response и finding. Запись одного пользовательского
действия выполняется одной транзакцией.

Для однопользовательского приложения используется обычный rollback journal, а
не WAL. Это убирает ненужную конкурентность и зависимость от исправления
WAL-reset в системной версии SQLite. Устанавливается разумный `busy_timeout`;
сервер остаётся одним процессом.

### `run.bat` и зависимости

`run.bat` не активирует окружение, а всегда вызывает конкретный
`.venv\Scripts\python.exe`.

Алгоритм запуска:

1. Найти Python 3.11–3.13.
2. Создать `.venv`, если интерпретатора окружения нет.
3. Сравнить установленные версии с `requirements.lock` и сохранённым отпечатком
   lock-файла.
4. Если всё совпадает — не запускать `pip` и не обращаться в интернет.
5. Иначе установить точные зависимости; `--proxy` передаётся только в эту
   операцию.
6. Запустить приложение с остальными аргументами пользователя.

Python автоматически не скачивается и не устанавливается. Ошибка отсутствующего
или неподдерживаемого Python должна быть короткой и понятной.

### Локальная защита

Сервер слушает только `127.0.0.1`, проверяет Host и не включает CORS. Все
изменяющие состояние HTML-формы получают случайный токен текущего запуска,
чтобы посторонняя страница не могла отправить запрос на localhost. Это не
создаёт логина или дополнительных действий для пользователя.

Ответы сервера получают CSP с `connect-src 'none'`, локальными script/style и
запретом внешних image/frame/object ресурсов. Поэтому содержимое ответа модели
не может инициировать сетевой запрос даже при ошибке renderer-а.

## Ключевые решения и их обоснование

| Решение | Альтернативы | Почему выбрано |
|---|---|---|
| Python-продукт в корне | Оставить его в `legacy/`; переписать заново | Уже реализованы история, кейсы, SQLite и стабильный UI. |
| Один Python parsing core | Два равноправных ядра; вызов Node из Python | Устраняет расхождение поведения и лишнюю runtime-зависимость. |
| Ручной copy/paste | DOM-интеграция; API модели | Надёжно, прозрачно и не зависит от интерфейса ChatGPT/Claude. |
| SQLGlot + собственные parsers | Полный ANTLR; только регулярные выражения | Даёт семантику SQL и точные исходные диапазоны без огромной grammar. |
| SQLite rollback journal | WAL | Однопользовательскому приложению не нужна параллельная запись; меньше рисков. |
| Точные зафиксированные зависимости | Широкие диапазоны в `pyproject.toml` | Воспроизводимый `run.bat` и отсутствие неожиданных обновлений. |
| Общий corpus в корне | Старые отдельные fixtures | Один набор требований, отсутствие молча пропущенных файлов. |
| Server-rendered UI | SPA | Текущий интерфейс уже достаточен, проще запуск и меньше зависимостей. |
| Ответ ИИ хранится как Markdown | Хранить очищенный HTML | Восстановление маркеров остаётся текстовым и точным; меньше поверхность XSS. |
| HTML буфера конвертируется на сервере после классификации | Конвертация в JS при paste; rich-text editor | Материалы Oracle не искажаются; конвертер покрывается pytest; не нужен JS-тулчейн. |
| Свой конвертер на `html.parser` | Turndown, markdownify | Разметка ChatGPT нестандартна (`data-d-component`, диаграммы); общие библиотеки склеивают блоки и не распознают диаграммы. |
| Рендер Markdown до восстановления маркеров | Рендер `restored_text` | Оригинальные значения показываются буквально и не ломают разметку. |
| `markdown-it-py` + `Pygments` + локальный mermaid | Рендер в браузере (marked, highlight.js) | Рендер и экранирование в одном месте на сервере; в браузер выносится только mermaid. |
| Парсинг форм с `max_part_size = 100 MiB` в `APIRoute` до `Form()` | Дефолт Starlette `1024 KB`; вызов `request.form` только в `Depends` | В FastAPI `get_request_handler` читает форму до разрешения `Depends`; кастомный `APIRoute` снимает лимит `1024 KB` для всех форм (`messages`, `revisions`, `from-material`, `artifacts`, `responses`) и позволяет вернуть HTML-ошибку вместо сырого JSON. |
| Контроль неизменности вставки в JS (`lastPastedPlain`) и фильтрация `pasted_html` на клиенте | Пересылка полной копии `pasted_plain` и любого `pasted_html` из IDE | Убирает трёхкратное раздувание POST-запросов и HTML-ответов при вставке больших планов из SQL Developer / DataGrip / DBeaver. |
| Копирование prompt напрямую из `<pre>` и анализ префикса 32 КБ в JS | Дублирующий скрытый `<textarea>` для каждого запуска; regex по всему тексту на каждый `input` | Убирает дублирование многомегабайтных промптов в DOM и предотвращает зависание вкладки браузера. |

## Отклонённые альтернативы и причины

### Продолжать подменять поле ChatGPT/Claude

Работа зависит от закрытого и регулярно меняющегося DOM. Даже успешный selector
не гарантирует корректную запись в framework-controlled editor и восстановление
streaming-ответа.

### Запускать TypeScript-парсер из Python

Потребуется Node.js или встраиваемый JavaScript runtime, усложнятся установка,
отладка и `run.bat`. Правила переносятся в Python один раз.

### Переписать локальное приложение на TypeScript

Не даёт пользовательской выгоды: готовые история, база, сервисы и web UI уже
существуют на Python.

### Сохранить две основные реализации

Это уже привело к расхождению corpus и исправлений. Расширение остаётся только
экспериментом.

### Шифровать SQLite и вводить авторизацию

Не соответствует согласованному доверенному локальному контуру. Ограничиваемся
localhost и защитой изменяющих запросов от чужих страниц.

### Хранить и показывать HTML ответа ИИ

Восстановление маркеров пришлось бы делать обходом DOM, маркеры могут быть
разорваны тегами. Нужен полноценный sanitizer. Цвета всё равно теряются,
потому что заданы CSS-классами чата.

### Rich-text editor вместо textarea

Тяжёлая зависимость. Риск искажения пробелов и выравнивания в Oracle-отчётах.

### Сохранять исходный HTML буфера рядом с ответом

Позволил бы переконвертировать старые ответы после улучшения конвертера, но
добавляет около 200 KB на ответ и новое поле схемы. Сейчас не нужен.

### Оставлять дефолтный `max_part_size = 1024 KB` и пересылать дубль `pasted_plain`

Дефолт Starlette рассчитан на публичные многопользовательские серверы, а в
локальном приложении блокирует вставку крупных планов `DBMS_XPLAN` / SQL Monitor
и раздутого `text/html` из IDE. Пересылка второй копии текста в `pasted_plain`
удваивает сетевой payload и размер DOM при перерисовке черновика.

## Риски и открытые вопросы

- SQLGlot может менять Oracle AST между версиями. Версия фиксируется lock-файлом,
  обновление выполняется только вместе с corpus-прогоном.
- Неизвестный формат Oracle может быть переобфусцирован целиком. Это допустимо;
  утечка чувствительного значения недопустима.
- Очень большой отчёт обрабатывается синхронно. Принимается лимит `100 MiB` на
  материал и поле формы (`MAX_ARTIFACT_BYTES` / `MAX_FORM_PART_BYTES`) и `10 MiB`
  на HTML буфера обмена (`MAX_CLIPBOARD_HTML_CHARS`); фоновые задачи не
  добавляются без измеренной необходимости.
- Corpus Oracle 21c не доказывает полную совместимость со всеми форматами 19c.
  Канонические 19c fixtures и пользовательские обезличенные примеры остаются
  обязательными.
- Разметка ChatGPT закрытая и меняется. Конвертер должен деградировать до
  абзацев и fallback на текст, а не падать. Fixtures буфера обновляются при
  обнаружении новых форматов.
- HTML Claude не проверен. До получения образца Claude обрабатывается
  семантической частью конвертера или fallback на текст.
- Карточки показателей ChatGPT видны только на скриншоте пользователя.
  Предполагается та же структура `data-d-component`, что у диаграмм.
- vendored `mermaid.min.js` 12.2.0 добавляет около 5,5 MB в пакет и
  PyInstaller-сборку.
- Блокирующих продуктовых вопросов нет.

## Стратегия проверки

Python loader рекурсивно обнаруживает каждый `.sql`, `.txt`, `.log` и `.out` в
`test-corpus`. `expectations.json` проходит JSON Schema validation. Для каждого
файла проверяются:

- ожидаемый тип;
- корректные и непересекающиеся диапазоны;
- минимальное количество распознанных значений;
- отсутствие всех `replace`, `PRIVATE`, `SECRET`, SQL ID, plan hash и query block
  значений после обфускации;
- сохранность `keep` и структурированных metric cells;
- exact round-trip;
- разрешённые parser findings.

Дополнительно проверяются усечения, CRLF/whitespace mutations, несколько отчётов
в одном вводе, повреждённые маркеры и случайно сгенерированные SQL.

Для ответов ИИ и больших форм проверяются:

- реальные образцы буфера ChatGPT (кнопка и выделение) в `tests/fixtures/clipboard/`:
  таблица, блоки кода с языком, mermaid, списки, отсутствие склейки блоков,
  фрагментированная selection-таблица и диаграмма в виде таблицы;
- OBF-маркеры внутри ячеек, кода и подписей диаграмм не экранируются и
  восстанавливаются;
- HTML при классификации материала игнорируется;
- рассинхронизация HTML и textarea приводит к fallback на текст;
- вставка планов и материалов размером > 1 MiB через текстовые поля всех HTML-форм
  (`messages`, `artifacts`, `revisions`, `from-material`, `responses`) проходит
  без ошибки `Part exceeded maximum size of 1024KB.`;
- превышение лимита размера формы/файла возвращает пользователю страницу с
  понятной ошибкой, а не сырой JSON Starlette;
- оригиналы со спецсимволами Markdown и HTML отображаются буквально;
- в отрендеренном ответе нет активного HTML и `javascript:`-ссылок.

Критерий релиза:

- все прежние Python service/web tests проходят;
- 49/49 текущих corpus-файлов проходят полный контракт;
- live Oracle Docker smoke проходит;
- `run.bat` проверен с чистым окружением, повторным запуском без сети и
  `--proxy`;
- localhost UI проходит основной пользовательский сценарий в браузере.
